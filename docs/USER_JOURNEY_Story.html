What you get, act by act — and what is still on you

✅ Works today, no caveats worth hiding

  • Record: a browser recorder that pierces shadow DOM and captures Salesforce field API names, not just CSS paths.
  • Safety first: the capture is validated before anything is derived. A secret that was flagged sensitive but not actually redacted aborts the run with exit 1 and writes no spec. (Loss below 50% is not caught — see the caveats.)
  • Derive: intent, entities, orchestration, guardrails and failure handling — each carrying the click or record-change that justifies it.
  • Honesty is scored: saying “I don’t know” earns points; deleting weak evidence to look cleaner cannot raise your score.
  • One name everywhere: topic, subagent, router action and test target all derive from a single function, so generated tests can’t point at a topic that doesn’t exist.
  • Repeatable: same capture in, same artifacts out. 764 tests passing as of 2026-07-25.

⚠️ Still on you — plan for this

  • Recording is a separate step. There is no record subcommand; you launch the recorder yourself, then feed the JSONL to the CLI.
  • The spec has no hands. It’s a topic router with zero actions — no @apex.* or @flow.* references. That is deliberate (inventing an action reference would be a fabrication), but it means you wire the actions.
  • Video input is a stub. Pass a video file and you get one placeholder step regardless of content. Use --capture.
  • The bundle isn’t emitted by the normal run. The writers exist and are tested; the call site is missing.
  • Deployment is fully manual and has never been validated against an org.
  • Two gates disagree: the in-process scorer passes at 75, the CI script at 85. A spec scoring 79 passes one and fails the other.
  • Fix ingest before you trust a run: the parser drops events the recorder legitimately emits, sub-50% loss is never reported, and a UTF-8 BOM eats the first event. All small fixes — but until they land, treat a low action count as suspicious rather than as a short process.
Read the score, then read the provenance. The same spec scores 79 (fail) with mock telemetry and 84 (pass) with live-org telemetry — a five-point provenance dimension is the entire difference. Today that dimension keys on a flag you pass on the command line, and the telemetry behind it is broadly-scoped queries matched to clicks by a 5-second window. Connecting an org makes the number go up without making the spec more correct. Treat 84 as “provenance was asserted”, not “behaviour was proven”.

Honest status of each link in the chain

LinkStateWhat that means for you
1 · Record partial A real capture-phase recorder with shadow-DOM piercing and 8 selector tiers. It has never been run against a live Lightning org, and it is not a pipeline stage — you invoke it separately.
2 · Ingest partial Raw events → coalesced, ordered, selector-ranked actions, byte-identical across repeat runs. But the parser rejects events the recorder legitimately emits, event loss below 50% is never reported, and a UTF-8 BOM silently drops the first event. Fixable, and worth fixing before any org run.
3 · Derive done This is the strongest part of the system. Confidence is capped rather than inflated: a well-evidenced Case update derives at 0.70, never 1.0.
4 · Review & score done A falsifiable gate: bad specs measurably fail, and deliberate attempts to game it mostly fail too (10 of 12 known attack vectors are blocked; 2 still squeeze through near the threshold).
5 · Run the spec repeatedly absent The half of your goal that says “run that spec over and over to improve it” does not exist yet. Nothing executes the spec, so no result returns. Needs a results parser and a real deploy-test-read cycle.
6 · Build as an Agentforce agent partial Every emitter is written; the bundle metadata matches the first-party template byte-for-byte. But nothing calls them from the normal run, and no org has ever validated the output.
The one thing to fix before trusting Act 6. The single script that produces these artifacts end to end currently labels the same agent three different ways in one run — the .agent file, the CLI --api-name, and the test suite’s subject each get a different name. A test run against that output would target an agent that does not exist. The library’s naming is correct and single-sourced; its one caller is not. Fix the caller before spending an org run on it.
